# The Cache That Never Grows

**DataForge 2026 — Pathway Track submission · Team: discodata**
Topic: *Key–Value Caching, Limitations, and Alternate Approaches* (Memory and learning)

## The one-sentence claim

> A fixed-shape recurrent state can process a sequence of unbounded length without allocating a new memory slot per token — but unlike a growing key–value cache, it forgets by **blending** old and new information together instead of **deleting** it outright.

The whole artifact exists to let a learner test this sentence with their own hands, not just read it.

## Who this is for

- **Audience:** ML/CS students and engineers who already know what a Transformer's KV cache is and are comfortable with dot products / matrix-vector products.
- **Prerequisites:** basic linear algebra (vectors, dot product, matrix-vector multiply); a rough idea of what "attention" computes. No familiarity with BDH is assumed — Part 3 introduces it from scratch.
- **Not required:** a GPU, an API key, or a BDH/BDH-CQ checkpoint. Everything runs client-side in the browser.

## Learning objectives

After using this artifact, a learner should be able to:
1. Explain why a Transformer's KV cache grows linearly with sequence length, and why that is a real deployment problem (StreamingLLM, H2O).
2. Explain, with a concrete equation, how a fixed-size recurrent ("fast-weight") state can absorb an unbounded number of tokens instead.
3. Predict — before running it — what happens to retrieval accuracy as more facts are packed into a fixed-size state, and why that failure mode looks different from cache eviction.
4. State where BDH and BDH-CQ actually sit in this picture, using the papers' own language, without overclaiming what a toy demo does or doesn't reproduce.
5. Name at least one way this explainer's toy model is *not* the same as real BDH.

### The interactive substrate, precisely

- **Facts:** each fact `i` is a pair of random unit vectors `(key_i, value_i) ∈ ℝ^D`, drawn once from a seeded Gaussian RNG (Box–Muller over `mulberry32`) and normalized.
- **KV cache:** stores `(key_i, value_i)` for the most recent `cap` facts (optionally with fact 0 pinned as an "attention sink," modeling Xiao et al. 2023). Querying fact `j`: if its pair is still stored, retrieval is exact. If evicted, the nearest surviving key by cosine similarity is returned instead — almost always the wrong fact.
- **Recurrent state:** a single `D×D` matrix `S`, updated additively after every fact: `S ← S + value_i · key_i^T`. Querying fact `j` computes `estimate = S · key_j` and decodes it via nearest-neighbor cosine similarity against all `N` true values seen so far.
- This additive rule is the classical "fast-weight programmer" / linear-attention associative memory (Schmidhuber, 1992). It is the same *family* of mechanism that BDH-CQ's own paper places its contextual memory within — **this is an original illustration, not a reimplementation of BDH or BDH-CQ.** See the explicit disclosure box in Part 3 of the artifact and in `SOURCES.md`.

### Verification performed before writing the guided walkthrough

Every caption in Part 1's three presets was checked against the literal output of `memory-model.js` (via a throwaway Node script) before being written, not assumed. Specifically we confirmed:
- Preset 1 (D=10, N=6, unlimited cache): both mechanisms retrieve fact 0 correctly (KV cosine=1.000, recurrent cosine=0.823).
- Preset 2 (D=10, N=20, cache capacity 8): fact 0 is evicted from the cache (cosine=0.132, wrong) and correctly restored once "pin fact 0" is enabled (cosine=1.000); with an unlimited cache the same setup stays exact.
- Preset 3 (D=10, N=60, unlimited cache): the cache still answers fact 5 exactly (cosine=1.000) while the recurrent state's answer degrades (cosine=0.504, decoded as a different fact entirely) — confirming the claim's asymmetry rather than assuming it.

## Reproducing the results

```bash
# Open directly — no server needed
open artifact/index.html          # macOS
xdg-open artifact/index.html      # Linux
# or double-click it / drag it into a browser tab

# To get a public URL for judging, push this repo to GitHub and enable
# GitHub Pages on the artifact/ folder, or drag the artifact/ folder into
# Netlify Drop / Vercel — no build step is required either way.

# To re-run the underlying math outside the browser (e.g. to check a claim
# without the chart's subsampling), Node can load memory-model.js directly:
node -e "
global.window = global;
require('./artifact/memory-model.js');
const MM = global.MemoryModel;
const facts = MM.getFacts(10, 200);
console.log(MM.queryRecurrent(facts, 60, 10, 5));
console.log(MM.queryKV(facts, 20, 8, false, 0));
"
```

Changing `BASE_SEED` in `memory-model.js` produces a different but qualitatively equivalent run — the story does not depend on the specific seed, only on the approximate crossover point between "cache still exact" and "state visibly interfering," which is a property of `N` vs. `D`, not of the seed.

## Setup instructions

None beyond a modern browser. No `npm install`, no API keys, no accounts. There is no third-party API call anywhere in this artifact, so the Rime-track credential/config-hygiene requirements do not apply here.

To regenerate `ONE_PAGE_SUMMARY.pdf` from source: `pip install reportlab matplotlib numpy && python3 docs/generate_charts.py && python3 docs/build_summary_pdf.py`. `generate_charts.py` produces `docs/figure.png` (an independent numpy re-implementation of the same fast-weight/KV-cache experiment, used as a cross-check on the JS artifact's math — see the figure caption in the PDF for what it shows); `build_summary_pdf.py` lays out the full one-page PDF around it. The full summary text lives in `build_summary_pdf.py`, not in a separate file, so there is exactly one place to edit it.
